# Journal — 2026-11-02

## Session — 22:59

**Summary:** This session ran from the morning of 1 November to the evening of 2 November and followed on from the 11:02 entry on 1 November. It started with housekeeping: merging the journal PR (#65), deleting stale branches and leftover agent worktrees. Then it turned to WBCodeFYName's real environment. The developer sent photos of the dev maker portal, which became `fields.md` and the dev step configuration. After a save in a William Buck environment failed, we worked out that the error was Microsoft's sandbox, not the plug-in. The product owner then dropped the rule that a WBCode must end in `70`, which became WBCodeFYName 0.2.0 (#80).

**Discussion & decisions:**
- **Branch cleanup:** the developer chose to delete stale branches locally and on the remote. Five of them were checked out in agent worktrees left from #39–#43. All five were clean and already on `main`, so the worktrees were removed too.
- **Photos:**
  - The developer asked for the photos of the dev tables to be pushed to `main`. I pointed out that they showed client WBCodes and Vault IDs, and they went in anyway.
  - Later the developer decided `fields.md` should be the record, and the photos were removed. They're still in history (`f9d65c2`, `740b1a7`). Rewriting `main` was offered but not taken up.
  - The developer's later error photos were read in the scratchpad and left untracked.
- **Confirmed names:** the photos settled the plug-in's target table, which had been open since the grilling session: `wbsuper_smsfmatter`, named in `wbsuper_wbcodefy` from the `wbsuper_wbcode` and `wbsuper_fy` lookups. The developer confirmed that the lookups point to SuperFundClient and Financial Year. The maker portal shows schema names, so the FY value column is `wbsuper_name`, not `wbsuper_Name`.
- **The `pac org fetch` error:** the runbook's column check failed in a William Buck environment with `The top attribute can't be specified with paging attribute page`. `pac` adds paging to every fetch, so the check uses `count='1'`.
- **The sandbox error:** a save failed with `no Sandbox Hosts are currently available` (reference `#DEF7D9B8`). The developer asked why the plug-in uses a sandbox at all: every custom plug-in in Dataverse online does. They also asked whether a code bug was the likely cause. The error code and stack trace pointed to Microsoft's sandbox rather than the code, with the environment's VNet setup as an outside chance. It cleared after a short wait.
- **The WBCode rule:** the product owner removed the `70` restriction. Any eight-digit WBCode is now accepted. The glossary still says `70` marks a super fund, because that's still what it means. Because the plug-in's behaviour changes, it's a minor version, 0.2.0, with `AssemblyVersion` left at 1.0.0.0.
