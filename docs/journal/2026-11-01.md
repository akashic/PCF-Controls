**Summary:** The developer put two new requirements files in the repo root: a Dataverse aggregate (count) PCF control and a synchronous PreOperation plug-in that builds a WBCodeFY primary name. Each got its own folder and a grilling session, and the decisions became two briefs, now ChoiceCounts and WBCodeFYName, with issues #50–#60. Four PRs (#61–#64) passed CI and were merged. The session ended on 1 November with CI on `main` green, the first run that built and tested a plug-in.

**Discussion & decisions:**
- The developer asked for the decisions one at a time, through the question panel, over six rounds. The briefs record the outcomes. These are the ones that shaped the code:
  - **ChoiceCounts**
    - Count is the only operation, but one control shows several counts: one badge per option of a Choice, Status Reason, Status or Yes/No column. It counts distinct primary IDs, and the maker can list a subset of options.
    - The maker narrows the count with a FetchXML fragment. It's allow-listed, `<link-entity>` included at the developer's request.
    - Failures show a neutral dash with a tooltip. A new record shows "Available after save". The record ID comes from the documented bound primary-key input, since PCF has no save event.
  - **WBCodeFYName**
    - Classic signed assembly, AssemblyVersion frozen at 1.0.0.0, logical names in the step's unsecure configuration.
    - Invalid input blocks the save. Lookups are retrieved as the calling user.
    - FY widened to `FY` plus two digits. Tests use MSTest and hand-written fakes; FakeXrmEasy was ruled out by its licence.
    - Registered from macOS with a Web API script, then `pac solution sync`, because the Plug-in Registration Tool is Windows-only.
- Mid-session the developer defined WBCode: a client's unique ID, the six-digit Client ID followed by a two-digit suffix, where `70` marks a super fund. It went into `GLOSSARY.md` and is the basis for the plug-in's WBCode check.
- Plug-ins live in `plugins/<Name>/`, one `WB<Name>` solution each, with the project one folder down so the SDK-style csproj doesn't compile `tests/` (ADR-0006). `check:controls`, CI and the release workflow now cover them.
- The briefs said net462. `pac` 2.14.1 generates net48, which is also the version Microsoft recommends, so the docs were corrected.
- The test project needed `System.Security.Cryptography.Pkcs` 6.0.5 to clear a high-severity advisory. That's a new NuGet package, so it went to the developer, who approved it and MSTest together before #63 merged.
